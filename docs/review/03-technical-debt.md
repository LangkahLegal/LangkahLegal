# 03 — Technical Debt and Improvement Candidates

> **Note (2026-10-12):** This review describes the backend before the layered refactor. The logic has since moved out of `backend/routers/*.py` into `backend/services/`, `backend/repositories/`, `backend/helpers/`, `backend/core/` and `backend/docs/`, so the file and line links below point to the old locations. Findings still open should be re-located by function name.

Findings are grouped by category, then sorted **high → medium → low** severity within each group. Effort: **S** = under a day, **M** = a few days, **L** = a week or more / needs design discussion.

## Authentication and authorization

| # | Severity | Finding | Risk | Effort |
|---|---|---|---|---|
| A1 | **High** | `PATCH /consultants/schedules/{id_jadwal}/toggle` has **no auth dependency at all** — no `Depends(get_current_user)`, no ownership check. [backend/routers/consultants.py:494-508](../../backend/routers/consultants.py#L494-L508) | Any unauthenticated caller who knows/guesses an `id_jadwal` can flip any consultant's slot availability (`status_tersedia`) on or off, disrupting bookings platform-wide. | S |
| A2 | **High** | `PUT /consultations/{id_pengajuan}/status` lets a `konsultan` caller set `new_status` to **any string**, with only an ownership check (must be their own pengajuan) — no allow-list of valid transitions. [backend/routers/consultations.py:152-182](../../backend/routers/consultations.py#L152-L182) | A malicious or buggy consultant client can push a `pengajuan_konsultasi` row into an invalid/unexpected status string, which other endpoints filter on with exact-match (`.eq("status_pengajuan", "terjadwal")`), silently breaking downstream flows (payment, history, dashboards) for that record with no server-side guardrail. | S |
| A3 | Medium | `PATCH /consultants/me/active-status` requires login but has **no role check** — any authenticated `client` can call it. [backend/routers/consultants.py:511-527](../../backend/routers/consultants.py#L511-L527) | Low practical impact today because the update is scoped `.eq("id_user", current_user["id_user"])` and a client has no `konsultan` row to match, so it's a harmless no-op — but it's an inconsistent pattern vs. every sibling endpoint in the same file, and becomes a real bug the moment a `client` row is ever given a `konsultan` counterpart (e.g. a user who changes role). | S |
| A4 | Medium | Access token and refresh token are stored in **`window.localStorage`** on the frontend (`ll_token`, `token`, `ll_refresh`, `refresh_token` keys), in addition to the backend also setting httpOnly cookies for the same tokens. [frontend/src/lib/authStorage.js:1-2,17-19,52-58](../../frontend/src/lib/authStorage.js#L1-L19), consumed by the axios interceptor at [frontend/src/lib/axios.js:100-104](../../frontend/src/lib/axios.js#L100-L104) | `localStorage` is readable by any JavaScript running on the page, so a single XSS vulnerability anywhere in the frontend is enough to exfiltrate long-lived session and refresh tokens. The backend already implements httpOnly cookie auth (`ll_token`/`ll_refresh`, see [routers/auth.py:65-87](../../backend/routers/auth.py#L65-L87)) — the frontend does not rely on it for API calls (axios sends `Authorization: Bearer` from localStorage instead, and `withCredentials: false` at [axios.js:51](../../frontend/src/lib/axios.js#L51) means cookies aren't even sent to the API). This means the more secure mechanism that already exists server-side is effectively unused for the SPA's own calls. | M |
| A5 | Medium | `POST /auth/login-password` has **no rate limit**, unlike `/login-otp`, `/resend-signup-otp`, and `/forgot-password`, which are all `@limiter.limit("3/minute")`. [backend/routers/auth.py:268-291](../../backend/routers/auth.py#L268-L291) | Password login is the one credential-guessing surface left completely open to brute force. | S |
| A6 | Low | `_get_supabase_user()` in `dependencies.py` is a full second implementation of token validation, dead and unused, sitting next to the real `get_current_user()`. [backend/dependencies.py:25-76](../../backend/dependencies.py#L25-L76) | Not directly exploitable, but a future maintainer could accidentally wire a new endpoint to the old/unmaintained helper (it lacks the email-fallback self-heal logic that `get_current_user` has), reintroducing already-fixed auth bugs. | S |
| A7 | Low | Rate limiting (`slowapi.Limiter`) is in-memory / per-process ([backend/limiter.py](../../backend/limiter.py)), with **no shared backend (Redis, etc.)** configured. | If the app is ever run with multiple worker processes/instances (common on Railway/most PaaS), each process tracks its own counters, so the effective rate limit is `N × configured limit` where `N` = worker count. Whether this matters depends on the current deployment's worker count — **unclear from codebase**. | M |

## Error handling and logging

| # | Severity | Finding | Risk | Effort |
|---|---|---|---|---|
| E1 | **High** | Two confirmed `NameError`-producing bugs: `frontend_base_url` is referenced but never assigned inside `assign_schedule_to_claim` ([backend/routers/consultations.py:521-538](../../backend/routers/consultations.py#L521-L538), used at line 532) and inside `sync_payment_status` ([backend/routers/payments.py:551-608](../../backend/routers/payments.py#L551-L608), used at line 602). Both are wrapped in a bare `except Exception as e: print(...)`. | Every time these code paths run, the notification email silently fails to send (a client/consultant never gets notified that a schedule was assigned or a payment settled via sync), and the failure is only visible in server logs via `print()`, not in any monitored error channel. This has presumably been failing 100% of the time since these lines were written. | S |
| E2 | High | Logging is inconsistent: `admin.py`, `admin_docs.py`, and `chatbot.py` use the standard `logging` module (`logger = logging.getLogger(__name__)`), while `cases.py`, `consultations.py`, and `payments.py` use bare `print(...)` for both info and error messages (e.g. [payments.py:242](../../backend/routers/payments.py#L242), [cases.py:273](../../backend/routers/cases.py#L273)). No `logging.basicConfig(...)` or structured-logging setup was found in `main.py`. | `print()` output bypasses log levels, structured fields, and whatever log aggregation is configured in production (Railway captures stdout, but there's no way to filter by severity, correlate a request, or alert on error-rate). Debugging a production incident means grepping raw stdout. | M |
| E3 | Medium | The generic exception handler in `chatbot_triage` returns internal exception details to the client: `detail=f"...Error: {type(e).__name__}: {str(e)[:300]}"`. [backend/routers/chatbot.py:384-389](../../backend/routers/chatbot.py#L384-L389) | Leaks internal implementation details (exception type names, truncated messages that may include fragments of SDK error responses) to any authenticated user hitting an error path. Low severity because it requires triggering a 500 and the endpoint is auth-gated, but it's still an information-disclosure smell worth cleaning up before a security-conscious audience sees it. | S |
| E4 | Medium | Broad `except Exception` blocks that swallow errors silently (no re-raise, no user-visible failure) are used around most notification-email sends (10+ call sites across `cases.py`, `consultations.py`, `payments.py`) and around the bursa-document fallback in `get_detail_pengajuan` ([consultations.py:403-420](../../backend/routers/consultations.py#L403-L420)). | Acceptable as a pattern for "best-effort email, don't fail the main request" — but combined with E2 (print-only logging), these failures are effectively invisible in production. Recommend keeping the swallow-and-continue behavior but routing all of them through `logger.error(..., exc_info=True)` so they're queryable. | M |
| E5 | Low | `create_transaction`'s Midtrans-status-check fallback treats **any** non-`"404" in str(e)` exception as a soft warning and falls through to create a brand-new transaction ([payments.py:117-126](../../backend/routers/payments.py#L117-L126)), string-matching on the exception message rather than an HTTP status code. | Fragile error discrimination — a transient network error unrelated to "not found" would be treated the same as a genuine 404, potentially double-creating Snap tokens for the same pending order under flaky network conditions. | S |

## API response consistency

| # | Severity | Finding | Risk | Effort |
|---|---|---|---|---|
| C1 | Medium | Response envelopes are inconsistent across the API: some endpoints return `{"data": ...}` (most of `consultations.py`, `cases.py`), some return `{"message": ..., "data": ...}`, some return the raw Supabase response object directly (`toggle_schedule_slot`, `toggle_global_active` in `consultants.py` return `db.table(...).update(...).execute()` verbatim — not even wrapped in a dict), and the chatbot router returns typed Pydantic response models with neither `data` nor `message` wrappers. | Frontend service functions have to know, endpoint-by-endpoint, whether to read `response.data`, `response.data.data`, or the raw body — visible in the frontend services themselves (compare [consultant.service.js:6](../../frontend/src/services/consultant.service.js#L6) `response.data.data` vs [consultant.service.js:16](../../frontend/src/services/consultant.service.js#L16) `response.data`). | C3 | Low | `status_pengajuan` string vocabulary mixes Indonesian and English (`dibatalkan` in most places, `cancel`/`cancelled` used at [consultants.py:647](../../backend/routers/consultants.py#L647) and [payments.py:293-294](../../backend/routers/payments.py#L293-L294)). | Any code (frontend or backend) that filters by exact status string can silently miss records depending on which write path produced them. | M (requires a data backfill + one canonical vocabulary) |

## Summary — top 5 to fix first

1. **A1** — unauthenticated schedule-toggle endpoint (S effort, high impact, fix now).
2. **E1** — the two `NameError` bugs silently killing notification emails (S effort, high impact, easy to verify and fix).
3. **A2 / V3** — add an `Enum`/allow-list for `status_pengajuan` transitions (S effort, prevents an entire class of downstream bugs).
4. **A4** — decide on one auth transport (cookie or bearer-from-localStorage) and stop shipping both; at minimum, stop storing tokens in `localStorage` if cookies are already implemented server-side.
5. **T1** — add at least smoke-level tests for `rag_service.agentic_generate` and `_smart_truncate` before the next change to the chatbot, since it currently has no regression safety net at all.
